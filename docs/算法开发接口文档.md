# 算法开发接口文档

> **给算法同学**: 这份文档告诉你数据采样完成后要干什么、怎么跟通信层对接、
> 以及怎么在 PC 上看到结果。**看完第 1~3 节就能开始写算法**,
> 后面是调试技巧和协议细节。

---

## 1. 你的任务 —— 填三个桩函数

打开 `main_template.c`,里面有三个标了 `TODO` 的桩函数,目前返回的都是假数据:

```c
static void preprocess(void);           // 预处理: 去直流、降噪
static void classify(wave_type_t *out); // 分类: 判四类波形
static void estimate(result_t *r);      // 参数估计: 频率、峰峰值、占空比
```

**输入**: 全局数组 `g_adc_buf[SAMPLE_COUNT]`,已由 DMA 填好,每个元素是
12 位 ADC 原始值 (0~4095)。

**输出**: 填到 `result_t` 结构体里:

```c
typedef struct {
    wave_type_t type;   // 波形类别: WAVE_SINE / SQUARE / TRIANGLE / SAWTOOTH
    float       freq;   // 频率, 单位 Hz
    float       vpp;    // 峰峰值, 单位 V
    float       duty;   // 占空比, 归一化 0~1 (非方波随便填,通信层会兜底成 0)
} result_t;
```

**接口约定** (见 `uart_report.h` 头部注释):

- `freq` / `vpp` 单位已定死,别自己换算
- `duty` 按"高电平样点数 ÷ 周期样点数"算 (0~1),通信层自动乘 100 变百分数
- 非方波的 `duty` 你随便给什么都行,通信层会强制改成 0
- NaN / Inf / 负数: 通信层有钳位兜底,但**算法不应该产生这些值** ——
  出现了说明有 bug,钳位只是防崩溃,不是让你依赖它

**主循环已经写好**,你只管实现那三个函数,其余的(采样触发、串口发送、
模式 B 上传)都不用管。

## 2. 编译 & 烧录 & 运行

### 2.1 编译 (CCS)

1. 把你的算法代码加到工程 (`classify.c` / `estimate.c` 之类),
   或者直接在 `main_template.c` 里把桩函数改成真实现
2. Build Project (Ctrl+B)
3. 有报错先看是不是这几个:
   - `undefined reference to sinf / sqrtf / ...` → 链到 `arm_math.lib`
     或打开编译器的 `-lm`
   - `multiple definition of ...` → 你和模板都定义了同名全局变量,
     改个名或加 `static`

### 2.2 烧录 & 运行

- Debug → Resume (F8),或直接 Run → Load → Run
- 单片机进入主循环后会通过 XDS110 虚拟串口不停发结果帧

### 2.3 PC 端接收 & 显示

打开一个终端,运行:

```bash
# 方式 1: 用队友写的 pc_receive.exe
pc_receive.exe COM5          # 端口号按实际情况改, COM10+ 会自动加 \\.\ 前缀

# 方式 2: 用我写的 pc_receiver.exe (多了环形队列和统计)
pc_receiver.exe COM5

# 方式 3: 串口助手 (115200, 8-N-1, 无流控)
# 能看到输出但要自己肉眼读, 不如上面两个程序直观
```

**正常输出长这样**:

```
[INFO] Opening \\.\COM5 (115200, 8-N-1, no flow control)
[INFO] Ready. Ctrl+C to exit.
[CTRL] #BOOT,MSPM0G3507 wave recognizer ready
type=sine      freq=   200.000 Hz  Vpp=   2.500 V  duty=  0.000 %
type=square    freq=   223.400 Hz  Vpp=   1.560 V  duty= 68.200 %
type=triangle  freq=   150.250 Hz  Vpp=   4.000 V  duty=  0.000 %
...
```

`#BOOT` 是上电提示,后面每一行对应一次识别。Ctrl+C 退出,程序会告诉你
一共收了多少条、最后一条是什么。

**常见问题**:

- **没输出**: CCS 的 Console 窗口和虚拟串口**同时**抢 XDS110,
  Serial Monitor 开着的话 PC 程序打不开 COM 口 → 关掉 Serial Monitor
- **乱码**: 串口助手编码选错了 → 输出是纯 ASCII,选 UTF-8 或 GBK 都行,
  但别选 UTF-16
- **一直报 "打开 COMx 失败"**: 端口号不对,或被别的程序占了 →
  设备管理器看 XDS110 Application/User UART 是哪个 COM,关掉占用的程序
  (Arduino IDE / PuTTY / ...),重插板子
- **频繁丢帧**: 数据线松了,或 USB hub 供电不足 → 换短线 / 直插 PC

## 3. 两种工作模式 (只有调 PC 端算法时才用模式 B)

`main_template.c` 头部有个宏:

```c
#define RUN_MODE_LOCAL_ALGO     1   // 1 = 模式 A, 0 = 模式 B
```

- **模式 A (默认, 正式比赛用这个)**: 单片机算完直接发结果帧,
  PC 只负责显示。你写的三个函数会被调用。
- **模式 B (可选, 调试用)**: 单片机把 4096 个原始 ADC 样点上传给 PC,
  由 PC 端 Python/MATLAB 算。**你的三个函数不会被调用**,编译时直接
  被条件编译排除掉。

**什么时候用模式 B?**

想在 PC 上跑算法 (Python 画图方便、改代码不用重新烧录),但又要用
真实的 ADC 数据而不是仿真信号 → 开模式 B,单片机当采集卡用。

**怎么收原始数据?**

`pc_receiver.c` 已经实现了,默认保存到 `raw_data.bin` (二进制) 和
`raw_data.txt` (CSV)。用 Python 读:

```python
import numpy as np
raw = np.fromfile("raw_data.bin", dtype=np.uint16)  # 4096 个 ADC 值
```

或者读 txt:

```python
raw = np.loadtxt("raw_data.txt", delimiter=",", dtype=int)
```

**模式 B 注意事项**:

- 4096 点 @ 115200 bps 要传 **1.7 秒**,主循环会卡在发送上,
  这段时间单片机干不了别的 → 只适合离线调试,不适合实时识别
- 传完一次单片机会**停住等你按键**才继续下一次采样 (见模板注释),
  避免一次还没传完又触发下一次把 buffer 冲了
- 想提速 → 把波特率改成 460800 (压到 0.4 秒),但要改两端,
  且 `pc_receive.c` 里 `CBR_115200` 要改成 `CBR_460800`,重新编译
- **队友写的 `pc_receive.c` 目前不支持模式 B** (见下文 §6 已知问题),
  要收原始数据请用 `pc_receiver.c`

## 4. 性能要求 & 时间预算

**官方限制** (初赛评分规则):

> "参赛队伍需在测试开始后 **10 秒内**在指定位置输出识别结果,
> 允许 **2 次重测**机会"

意思是每个测试信号给你 10 秒,算不出来或输出格式错就 0 分,最多允许
重测 2 次 (硬件问题、接触不良之类)。**算法必须在 10 秒内出结果**。

**时间都花在哪?**

- **ADC 采样**: 4096 点 @ 20 ksps = **0.2 秒** (这是物理极限,省不掉)
- **算法计算**: 目标 **< 0.5 秒** (留 9.3 秒余量给裁判操作 + 重测)
- **串口发送**: 一帧 37 字节 @ 115200 bps ≈ **0.003 秒** (可忽略)

**优化建议**:

- 别在主循环里调 `printf` 往 CCS Console 打 log,那个**巨慢**
  (一次 `printf` 可能 10ms+),会把 10 秒吃光 → 用 GPIO 翻电平 +
  逻辑分析仪,或者只在 Debug 配置开 printf、Release 配置全关
- FFT 用 CMSIS-DSP 的 `arm_cfft_q15` (定点) 而不是 `arm_cfft_f32`
  (浮点),M0+ 没 FPU,浮点慢 10 倍+
- 大数组 (`float buf[4096]` 之类) 用 `static` 或全局,别放栈上 ——
  MSPM0 默认栈只有 1KB,放栈上直接炸
- 除法改乘法、`powf(x, 2)` 改 `x*x`、三角函数能用查表就查表

**怎么测算法耗时?**

```c
#include "ti_msp_dl_config.h"  // 已经 include 了

uint32_t t0 = DL_Common_getTIMGClockCount(...);  // 开始
preprocess();
classify(&g_result.type);
estimate(&g_result);
uint32_t t1 = DL_Common_getTIMGClockCount(...);  // 结束
// 周期数转毫秒: (t1 - t0) / (SYSCLK_HZ / 1000)
```

或者懒得写代码 → CCS 的 Profiler (Run → Load → Profile),自动统计
每个函数的调用次数和耗时占比。

## 5. 数据格式 & 评分规则速查

### 5.1 输出格式 (已由通信层搞定,你只管填结构体)

单片机会发:

```
RESULT,<type>,<frequency>,<Vpp>,<duty>\r\n
```

例如:

```
RESULT,sine,200.000,2.500,0.000
RESULT,square,223.400,1.560,68.200
```

- 所有数值保留三位小数 (通信层自动格式化)
- 类别词小写英文: `sine` / `square` / `triangle` / `sawtooth`
- 占空比单位是 **百分数 %** (你给 0~1,通信层乘 100)
- 非方波占空比恒为 0 (通信层强制,你随便填)

### 5.2 评分规则 (初赛)

**总分 100 = 类别 15 + 频率 35 + 峰峰值 35 + 占空比 15**

类别识别与参数估计**独立计分** → 类别认错了,频率 / 峰峰值 / 占空比
仍然按相对误差正常给分,**所以无论如何都要发帧,不要因为不确定就不发**。

参数估计按相对误差 $e = \frac{|测量值 - 真值|}{真值}$ 分三档:

| 相对误差 $e$     | 得分占比 |
|-----------------|---------|
| $e \leq 5\%$    | 100%    |
| $5\% < e \leq 50\%$ | 40% |
| $e > 50\%$      | 0%      |

**举例**: 频率真值 200 Hz,你输出 210 Hz → $e = 5\%$,拿满 35 分;
输出 250 Hz → $e = 25\%$,拿 $35 \times 0.4 = 14$ 分;
输出 350 Hz → $e = 75\%$,0 分。

**注意**:

- **占空比只有方波计分**,其它波形这 15 分直接没有 (不是 0 分,是不算)
- 单位搞错 (占空比给成 0~1 而不是 0~100,或者反过来) →
  $e$ 接近 100% 或 9900%,必定 > 50%,**直接 0 分** →
  这个坑通信层已经帮你填了,你按 0~1 给就行
- NaN / Inf / 超大数 → 通信层会钳位,但 $e$ 仍然巨大,拿不到分 →
  **算法本身不要产生 NaN/Inf**,那是 bug

## 6. PC 接收程序现状 & 已知问题

目前有**两个**独立的 PC 接收程序:

### 6.1 `pc_receiver.c` (我写的,功能完整)

- ✅ 模式 A 结果帧: 解析 + 显示 + 环形队列
- ✅ 模式 B 原始数据: 接收 + 校验和 + 保存到 `raw_data.bin` / `.txt`
- ✅ 控制行 (`#BOOT` / `#ERR`) 正确识别
- ✅ 协议 2.8 节五条容错规则全部实现
- ✅ 端到端测试 27 例全过
- 编译: `gcc -std=c99 -Wall -Wextra pc_receiver.c -o pc_receiver.exe`

### 6.2 `pc_receive.c` (队友写的,更简洁但有 bug)

- ✅ 模式 A 结果帧: 解析 + 显示
- ✅ 控制行识别
- ✅ 环形队列
- ✅ COM10+ 自动加 `\\.\` 前缀
- ❌ **模式 B 原始数据会被误判成结果帧** (实测: 4096 点会被当成
  几十个 `unknown` 类型的结果,刷屏且污染统计)
- ❌ 缺 `#RAW` / `#END` 状态机,只是把它们当普通控制行打印
- 编译: `gcc -std=c11 -Wall -Wextra pc_receive.c -o pc_receive.exe`
  (或 `cl pc_receive.c`)
- 测试: `test_pc_receive.c`,31/32 过 (模式 B 那条失败)

**Root cause**: `pc_receive.c` 的 `parse_line()` 只检查行首是不是 `#`,
是的话就当控制行,不是就尝试按结果帧解析。原始数据的数据体
(例如 `2048,2085,2122,...,2603`) 没有 `#`,且有 16 个逗号分隔的数字,
所以会被当成 "类别=unknown,freq=2085,vpp=2122,duty=2159" 这种鬼畜结果。

**修复方法** (如果要用 `pc_receive.c` 收模式 B):

加一个全局状态 `int g_raw_active = 0`,遇到 `#RAW` 时置 1,遇到 `#END`
时置 0。`parse_line()` 开头加一句:

```c
if (line[0] == '#') {
    if (strncmp(line, "#RAW,", 5) == 0) {
        g_raw_active = 1;
    } else if (strncmp(line, "#END,", 5) == 0) {
        g_raw_active = 0;
    }
    printf("[CTRL] %s\n", line);
    return 1;
}
if (g_raw_active) {
    return -1;  // 静默丢弃数据体行
}
// ... 后面正常解析结果帧
```

**建议**: 模式 A 随便用哪个都行;模式 B 目前请用 `pc_receiver.c`,
或者改完 `pc_receive.c` 后重跑 `test_pc_receive.c` 确认 32/32 过。

## 7. 协议细节 (出问题时再看)

### 7.1 波特率 & 端口

- **115200, 8-N-1, 无流控** (写死在 SysConfig 和通信层里)
- XDS110 虚拟出两个串口:
  - **Application/User UART** ← 这个才是你的,看设备管理器确认 COM 号
  - Auxiliary Data Port ← 给调试器用,别选错
- COM10 及以上 Windows 要求写成 `\\.\COM10`,两个接收程序都已处理

### 7.2 帧结构

```
RESULT,<type>,<freq>,<Vpp>,<duty>\r\n
^^^^^^^                            ^^
前缀(可选) 四个字段用逗号分隔     结束符(CR+LF)
```

- 前缀 `RESULT,` 可以省略 (发送端宏 `REPORT_FRAME_WITH_PREFIX`),
  两个接收程序都兼容
- 字段内**不允许有空格** (逗号前后都不能有),但两个接收程序会 trim
  掉字段首尾空白,所以有空格也不会炸
- 结束符必须是 `\r\n` (CR + LF),只有 `\n` 也能收,只有 `\r` 不行

### 7.3 控制行 (以 `#` 开头)

```
#BOOT,MSPM0G3507 wave recognizer ready   ← 上电提示
#ERR,frame format failed                 ← 拼帧失败(罕见)
#RAW,<n>,<fs>                            ← 模式 B 原始数据帧头
#END,<checksum>                          ← 模式 B 帧尾(32 位累加和)
```

你的算法代码**不需要管这些**,除非要自己发调试信息 → 用
`report_send_comment("你的消息")`,别直接 `uart_send_str`,
不然会漏掉 `#` 前缀,PC 端会报解析失败。

### 7.4 容错规则 (协议 2.8 节)

接收端会:

1. **静默丢弃**空行 / 纯空白行 / 字段不足 4 个 / 数字非法 (含字母) 的帧
2. 字段多于 4 个 → 取前 4 个,多余忽略
3. 类别词不在枚举内 (`noise` / `sin` / ...) → 标为 `unknown`,
   数值照常解析 (类别与参数独立计分)
4. 超长行 (> 256 字节) → 整行丢弃,不影响后续帧

**所以**: 偶尔发错一帧 (算法崩了输出 NaN、UART 收到一个毛刺) 不会导致
后续所有帧都挂掉,接收端会自动恢复。但**不要依赖这个容错机制** ——
发出去的每一帧都应该是合法的。

## 8. 常见算法问题排查

### 8.1 频率总是偏高 / 偏低

- **采样率配置错了**: `SAMPLE_RATE_HZ` 与 Timer 实际触发频率不一致 →
  检查 SysConfig 的 Timer 配置,算一遍 `SYSCLK / (Prescaler × Load)`
- **周期检测把一个峰当成两个**: 阈值太敏感,噪声也触发了 →
  提高阈值,或先做中值滤波
- **整数除法截断**: `freq = SAMPLE_RATE_HZ / period` 写成整数除法了 →
  改成 `freq = (float)SAMPLE_RATE_HZ / period`

### 8.2 峰峰值总是偏小 / 偏大

- **ADC 参考电压**: MSPM0 的 ADC 参考电压是 **VDDA (3.3V)** 或内部
  2.5V,看你 SysConfig 选的哪个 →
  Vpp = (ADC_max - ADC_min) × VREF / 4096 × 分压系数
- **没减直流**: 信号有 1.65V 直流偏置,你直接 `max - min` 会多算一倍 →
  先减均值再找峰峰值
- **饱和**: 信号幅度太大,ADC 读数一直是 4095 / 0 → 调信号源幅度,
  或改分压电路

### 8.3 方波占空比总是 50%

- **阈值不对**: 方波本身有过冲 / 下冲 / 振铃,简单取中值当阈值会偏 →
  用迟滞阈值,或者 20% / 80% 分位数
- **只数了一个周期**: 前 / 后半个周期正好被截断,数出来 50% →
  找完整周期,或平均多个周期

### 8.4 三角波 / 锯齿波分不清

- **只看了单调性**: 三角波是"上升 → 下降",锯齿波是"上升(快) →
  下降(慢)"或反过来,但如果只判"有上有下"那俩没区别 →
  比较上升段和下降段的**斜率 / 时长**,差 3 倍以上才是锯齿波
- **采样点不够**: 20 ksps 对 400 Hz 只有 50 点/周期,锯齿波的陡边
  只有几个点,不明显 → 换个判据,或者提高采样率(硬件允许的话)

### 8.5 性能瓶颈

- **FFT 太慢**: 4096 点浮点 FFT 在 M0+ 上跑几百毫秒是正常的 →
  换 CMSIS-DSP 的定点 FFT,或者用时域法 (自相关 / 过零检测)
- **大数组拷贝**: `memcpy(dst, src, 4096*sizeof(float))` 也要几毫秒 →
  能 in-place 就别拷,或者用指针交换
- **printf 拖累**: 前面说过了,关掉

## 10. 快速自检清单 (提交前过一遍)

- [ ] 三个桩函数都换成真实现了,没有 `TODO` 注释
- [ ] `result_t` 的四个字段都有赋值,没有未初始化变量
- [ ] `duty` 单位是 0~1,不是 0~100
- [ ] 非方波的 `duty` 随便给了个值 (0.0f 或 0.5f 都行,反正会被改)
- [ ] 编译无警告 (`-Wall -Wextra` 全开)
- [ ] 烧录后 PC 端能收到帧,不是乱码也不是静默无输出
- [ ] 用信号发生器喂已知信号 (200Hz 正弦 2Vpp 之类),输出值在 ±5% 以内
- [ ] 算法耗时 < 0.5 秒 (Profiler 或计时器测过)
- [ ] 四类波形都试过,没有哪类永远识别不出
- [ ] 方波占空比在 30% / 50% / 70% 时输出值都对
- [ ] 极端情况 (100Hz / 400Hz / 最小幅度 / 最大幅度) 都能出结果,
  不会卡死 / 输出 NaN / 崩溃重启

## 附录 B: 遇到问题找谁

| 问题类型 | 找谁 | 方式 |
|---------|-----|-----|
| **算法**: FFT / 滤波 / 特征提取 | 算法组长 | 微信 / 当面 |
| **硬件**: 板子不亮 / 烧录失败 / 引脚 | 硬件负责人 | 微信 / 当面 |
| **通信层**: 帧格式 / PC 接收 / 协议 | 我 (通信负责人) | 微信 / issue |
| **CCS**: 编译错误 / 链接错误 / 调试 | 先查官方文档,再问组里 | Google / 微信群 |
| **TI 芯片手册**: 寄存器 / 外设配置 | TI 官网 datasheet | https://www.ti.com |

**千万别卡住不说** —— 卡半天浪费时间,问一句可能 1 分钟就解决了。
